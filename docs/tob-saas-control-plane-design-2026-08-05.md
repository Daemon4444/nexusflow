# NexusFlow ToB SaaS 与多上游控制面设计

> 状态：Proposal，不代表已实现或已上线。
> 日期：2026-08-05。
> 目标：统一企业、成员、子账号和转售边界，并把现有 Provider 后端能力升级为可运营、可发布、可回滚的控制面。

## 1. 核心决策

### 1.1 企业与子账号不应作为两个平级产品

二者相似，但不是同一个对象：

- 企业（Organization / Workspace）是租户、权限、结算和政策边界。
- 成员（Member）是真人登录身份，通过 membership 加入企业并获得角色。
- 服务账号（Service Account）是程序或项目身份，持有 API Key、预算、模型权限和速率限制。
- 当前子账号同时承担“团队成员登录”和“消费执行主体”，概念过载；应逐步迁移为企业下的服务账号兼容层。

建议产品入口统一为“工作区”，原“子账号”和“企业中心”不再并列：

```text
工作区
├── 总览
├── 成员与访问
│   ├── 成员
│   ├── 团队与角色
│   ├── 服务账号（兼容现有子账号）
│   └── API Key
├── 用量与预算
│   ├── 按成员 / 服务账号 / 项目分账
│   ├── 预算与限额
│   └── 速率限制
├── 模型与策略
│   ├── 可用模型
│   └── 企业路由 / 地域 / SLA 策略
├── 账单与合同
└── 商业化（仅 reseller-enabled）
    ├── 产品与价本
    ├── 下游客户
    ├── 品牌与域名
    └── 对账与结算
```

个人用户也应拥有一个默认个人工作区，从而让 API Key、用量和账单都具备统一的 `workspace_id`，避免个人版和企业版长期维护两套模型。

### 1.2 不做任意层级的“企业套企业”

转售场景采用清晰的一层关系：卖方企业 → 下游客户账户。不要允许无限递归组织树。下游客户账户可以独立拥有用户、Key、价本和账单，但资金与合同关系必须显式指向卖方企业。

### 1.3 钱属于结算账户，不属于成员

保留现有主账号资金权威和 `actor_user_id` 证据，同时演进为：

- `billing_account`：余额、信控或企业账期的资金权威；
- `workspace`：租户和政策边界；
- `principal`：成员或服务账号，作为消费 actor；
- `project/cost_center`：可选的成本归集维度。

任何迁移都必须保留旧主/子账号账本和历史导出语义。

## 2. 当前体验审计

证据位于 `docs/audits/tob-saas-2026-08-05/`。

1. 企业总览：视觉健康，但只覆盖企业配置与商业化入口；成员、服务身份、预算和现有子账号没有形成一个工作区模型。
2. 子账号列表：功能完整度尚可，但和企业成员重复；“创建子账号”一次塞入登录凭据、额度、周期和 70+ 模型，认知负担过高。
3. Provider 总览：数据真实性表达清楚，但全部是只读表格；Provider 行不可进入运营详情，也没有主要操作。
4. 承载路由：能看到 75 条真实路由、容量、成本和健康，但无法在同一模型下比较候选上游、编辑映射、模拟策略或发布变更。
5. 运营问题：能列出问题，但 22 个告警只是纵向信息流，没有负责人、状态、合并去重、修复动作、事件时间线或静默规则。

可见的可访问性风险：创建子账号弹窗内容过长，操作按钮可能离开首屏；模型选择依赖长列表，键盘和屏幕阅读器用户需要更明确的分组计数、批量操作结果与焦点恢复。完整键盘、焦点、对比度和读屏验证仍需专项测试。

## 3. 多上游能力判断

结论：数据面已有真实多 Provider 选路基础，但控制面和供应链模型仍不够完整。

### 3.1 已有能力

- 同一 canonical model 可在 `provider_capacity` 配置多个 Provider 路由；
- Provider 级优先级、权重、RPM、TPM、每日量和并发限制；
- 渠道配置、区域、模型 allowlist 与加密凭据；
- 客户级 route policy：允许/阻止、固定、最低成本、健康优先；
- 成本版本、来源证据、健康记录、SLA 快照和变更审计；
- Redis 跨节点容量租约与 fail-closed 行为。

### 3.2 主要缺口

1. 新 Admin 只读：后端已有渠道、容量、路由策略和审计写接口，界面没有组织成安全的操作流。
2. Provider 模型映射过粗：`provider_models.model_id` 全局唯一，缺少 canonical model → provider-specific upstream model ID、协议、参数模板和 capability override 的正式映射实体。
3. Channel 仍是 JSON 配置：不利于独立健康、独立容量、凭据轮换、审计、查询和灰度发布。
4. “权重”并非真正流量比例：当前调度计算分数后确定性选择最高分，不是按权重随机/平滑分流。
5. 渠道选择同样以最高 priority 为主，缺少独立熔断、按请求重试链和可解释的 fallback sequence。
6. 成本选路缺少请求 Token 预估，当前只能用最高有效价格档保守判断。
7. 缺少变更发布模型：没有 draft → validate → approve → canary → publish → rollback 的策略版本。
8. 告警不是事件管理：没有 owner、acknowledge、resolve、mute、runbook 和关联发布。

## 4. Admin 目标信息架构

```text
平台控制台
├── 运营总览
├── 流量与请求
├── 供应侧
│   ├── Provider
│   ├── 渠道与凭据
│   ├── 模型映射
│   └── 容量与配额
├── 路由中心
│   ├── 路由矩阵
│   ├── 客户 / 企业策略
│   ├── 策略模拟器
│   └── 发布与回滚
├── 成本与毛利
│   ├── 合同 / 价本
│   ├── 成本覆盖
│   └── 毛利风险
├── 可靠性
│   ├── 健康与熔断
│   ├── 事件中心
│   └── SLA
├── 客户与企业
├── 财务与账本
└── 治理
    ├── 权限
    ├── 审计
    └── 发布中心
```

### 4.1 Provider 详情页

每个 Provider 应有独立详情，而不是表格一行：

- 概览：状态、合同、负责人、近 24h 成功率/延迟/成本/流量；
- 渠道：endpoint、region、credential reference、健康、容量、最后验证时间；
- 模型映射：canonical ID、upstream ID、协议 adapter、能力覆盖；
- 容量：RPM/TPM/并发/每日量，当前占用与阈值；
- 成本：价本版本、档位、来源、有效期和覆盖缺口；
- 事件：失败、熔断、人工切换和关联发布；
- 变更：审批原因、diff、操作者和回滚点。

### 4.2 路由工作室

以 canonical model 为中心展示 Provider × Channel 候选矩阵。主要操作必须支持：

1. 编辑上游模型映射和协议；
2. 配置优先级、真实流量权重、地域、成本/SLA 门槛；
3. 输入一个客户、区域、Token 规模和协议进行 dry-run，显示逐层过滤原因和最终候选；
4. 保存草稿并生成 diff；
5. 审批后按 1%/5%/20%/100% 发布；
6. 依据错误率、延迟、账本和容量门禁自动回滚。

## 5. 建议数据模型

采用 expand-only 演进，不直接删除现有表：

- `workspaces` / 扩展现有 `organizations`：统一个人与企业租户；
- `workspace_members`：真人成员与角色；
- `service_accounts`：程序身份，兼容现有 `users.parent_user_id` 子账号；
- `billing_accounts`、`cost_centers`：结算与归集；
- `provider_endpoints`：把 channel JSON 迁为一等实体；
- `provider_model_mappings`：canonical model 与上游模型/协议映射；
- `route_policy_versions`、`route_publications`：策略版本、灰度和回滚；
- `provider_incidents`：事件生命周期；
- `provider_contracts` / `price_books`：合同与成本来源。

Provider 凭据只保存 secret reference / 密文，不在 Admin 接口返回可还原明文。

## 6. 实施顺序

### Phase 1：统一客户工作区

- 导航合并为“工作区”；
- 企业成员、现有子账号和 API Key 汇入“成员与访问”；
- 子账号改名为“服务账号”，保留旧 URL/API 兼容；
- 用量按成员/服务账号统一分账。

### Phase 2：可操作的供应控制面

- Provider 详情页；
- Channel/endpoint 一等实体；
- 模型映射与容量编辑；
- 所有写操作强制 reason、权限、审计和敏感字段遮罩。

### Phase 3：路由发布系统

- 路由矩阵与模拟器；
- 版本化策略、审批、灰度、自动门禁和回滚；
- 将 weight 语义升级为可验证的真实流量分配。

### Phase 4：企业转售闭环

- 下游客户账户、产品、价本、合同和账单；
- 独立品牌/域名；
- 卖方企业与平台的收入、成本、应收和分润对账。

## 7. 当前建议

下一次代码迭代优先做 Phase 1 和 Phase 2 的骨架，不先做正式转售收款。这样能先消除“企业中心 vs 子账号”的产品冲突，同时把已有但隐藏的多上游后端能力变成可安全运营的控制面。
